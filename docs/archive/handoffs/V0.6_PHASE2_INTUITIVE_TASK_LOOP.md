# Local Creative OS v0.6 Phase 2

## Intuitive Task Loop

本阶段冻结一条不要求创意人理解内部语义的主流程：

```text
选中内容 → 输入修改要求 → 确认执行 → 自动追踪 → 结果确认
```

内部仍保留 Target、Context Snapshot、Command、Run、Revision、Decision 等对象，但它们在用户动作之后自动生成，不再成为黄金路径上的手动入口。

## 1. Work Rail 自动模式

右侧工作栏保持单实例与常驻 Composer。中部内容由状态自动决定：

| 条件 | 自动模式 |
|---|---|
| 无选择、无任务 | 当前工作视角摘要 |
| 单选 / 大预览 | 文件预览、备注、版本与关联摘要 |
| 多选 | 自动判断修改目标与参考资料 |
| queued / running / failed | 当前任务状态 |
| waiting_input | 需要用户确认的问题 |
| review + Pending Artifact | 版本比较与接受 / 继续修改 |
| accepted + 当前结果被选中 | 当前版本详情与接受完成提示 |

模式优先级由 `state/workRailMode.ts` 统一定义，避免组件内部继续堆叠互相冲突的条件判断。

## 2. Composer 合同

Composer 始终位于 Work Rail 底部：

- `C` 聚焦输入框；
- `Ctrl/Cmd + Enter` 进入发送前确认；
- 单选时自动将唯一可编辑内容作为 Target；
- 多选中只有一个可编辑主文件时，其他内容自动作为 Context；
- 多个可编辑文件时只询问“主要修改哪个文件”；
- queued / running / waiting_input 期间可记录下一步想法，但暂不允许创建第二个 Fixture Run；
- review / completed 后可以继续发起下一轮修改。

## 3. 执行追踪

点击确认面板中的“开始执行”之后才自动生成：

- Command ID；
- Context Snapshot ID；
- Run ID；
- Canvas Process Node；
- Target → Run 的修改关系；
- Context → Run 的引用关系。

运行完成后，Process Node 自动切为紧凑模式，保留追溯但不继续抢占 Canvas。

## 4. 自动状态闭环

```text
queued
→ running
→ waiting_input
→ running
→ review
→ completed
```

- waiting_input 自动占据工作栏中部，用户不必寻找 Activity；
- Artifact Return 自动进入 Pending Return Zone；
- Work Rail 自动切换到 Compare / Review；
- “继续修改”会选择返回的 Draft、聚焦 Composer，并将它作为下一轮 Target；
- “接受为当前版本”后，返回 Artifact 晋升为 Working / Current；
- 旧目标归档，生成关系停止流动；
- Process Node 折叠；
- 工作栏回到当前文件详情，并展示“已接受为当前版本”；
- 提示创建 Checkpoint。

## 5. 本阶段保留的 Phase 1.1 修复

- 发送前确认面板居中于 Canvas 可用区域；
- 打开确认面板时 Canvas 完全锁定；
- 遮罩手势不关闭面板、不解除锁定；
- Canvas Pointer / Wheel / RAF 三层保护；
- 面板使用静态遮罩，不启用高频背景模糊；
- ProjectCanvas 保持 memoized，Composer 输入不触发整张 Canvas 重渲染。

## 6. 本阶段不做

- 真实 Local Core / Bridge / Codex Runtime；
- 并行多个真实 Run；
- 用户手动编辑完整 Context Pack；
- Skill 编排画布；
- 区域标注；
- 完整 Delivery；
- Phase 3 的 Project Drive / Canvas Scope 进一步扩展。

现有 Project Drive、Root / Child Canvas Scope、面包屑和自动布局基础代码保留，但本轮验收只围绕任务闭环。
