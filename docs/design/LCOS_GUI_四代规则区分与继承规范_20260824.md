# LCOS GUI 四代规则区分与继承规范

> 日期：2026-08-24  
> 性质：GUI 历史规则分层、冲突裁决与后续施工约束  
> 适用对象：Codex、WorkBuddy、UI 设计与前端执行者  
> 目的：防止 AdFrame、Huabu/PASS8、Spatial 三视图、Glaze/Glyth 四代规则继续混用

## 1. 结论先行

LCOS GUI 目前存在四代设计规则。四代并非平级，也不是后出现的一代完全推翻前一代，而是按不同职责继承：

```text
第一代 AdFrame
提供 Preview / Review / Compare 等局部审阅能力
        │
        ▼
第二代 Huabu / PASS8
提供 Ghost、Semantic Drop、ChangeSet 和 Agent 可见修改机制
        │
        ▼
第三代 Spatial + Main / Context / Workflow
定义正式的数据、Presentation、Canvas 与三大工作现场架构
        │
        ▼
第四代 Glaze + Glyth
定义最新组件形态、动态语言、直接操纵与 Agent 搭建能力
```

当前发生规则冲突时，按以下顺序裁决：

1. Project Truth、Presentation 和三大 Surface 的正式架构边界；
2. Glaze / Glyth 最新组件、形态与动态语言；
3. Huabu / PASS8 中仍有效的 Ghost、Drop、ChangeSet 等交互基础；
4. AdFrame 中仍有效的 Preview、Review、Compare 局部能力；
5. 旧三栏 Shell、统一白卡和旧 DotGlyph 中心化规则不再具有约束力。

---

## 2. 第一代：AdFrame 三栏审阅工作台

### 2.1 当时解决的问题

第一代围绕 AIGC 内容审阅建立：

```text
左侧素材与版本
→ 中央媒体预览
→ 右侧评测、属性与评论
```

主要参考 Frame.io V4、Dropbox Replay、DaVinci Resolve、Runway、Label Studio、CVAT、FiftyOne、W&B Evaluations、Notion 与 Linear。

### 2.2 典型 GUI 规则

- 固定三栏工作台；
- 深色专业审阅气质；
- 中央媒体预览占据主要空间；
- 左侧承载素材、版本与导航；
- 右侧承载 Inspector、评分和评论；
- 底部承载分享、导出与审阅动作；
- 产品主流程围绕“打开一个内容并评审”组织。

### 2.3 继续保留

- 图片、视频、PDF、PPT 等文件预览；
- 版本比较；
- 评论、批注与 Review；
- Accept / Retry；
- 当前页、当前帧定位；
- Inspector 的局部导航；
- 沉浸式文件阅读与审阅模式。

### 2.4 明确废弃

- 三栏作为 LCOS 总体 App Shell；
- Inspector 永久常驻；
- 所有项目围绕单一媒体审阅组织；
- 把 Main、Context、Workflow 塞进固定三栏；
- 用旧 AdFrame 节点和面板规范指导当前空间节点；
- 用暗色审片台气质统治整个 LCOS。

### 2.5 当前地位

```text
AdFrame = Review 子能力来源
AdFrame ≠ LCOS 总体 GUI 规则
```

## 3. 第二代：Huabu / PASS8 Human + Agent 画布

### 3.1 当时解决的问题

第二代尝试把静态审阅界面推进为 Human + Agent 共用画布：

```text
用户在画布操作
→ Agent 提出整理或修改
→ GUI 显示 Ghost Preview
→ 用户 Keep / Revert
```

主要参考 Huabu 的协作模式、XYFlow 的部分交互、iOS 式轻量浮层与 AirDrop 式投送反馈。

### 3.2 典型 GUI 与交互规则

- Gesture Preview Store；
- Ghost Preview；
- Agent ChangeSet；
- Keep / Revert；
- stale fail-closed；
- Selection Outline；
- Near-field Toolbar；
- Semantic Drop；
- Drop Shelf；
- Light Curtain；
- DotGlyph 状态语言；
- Agent 修改过程必须可见。

### 3.3 继续保留

- 瞬时交互状态与正式持久化分离；
- Ghost 未确认不得写入 Project Truth；
- Agent 不得静默覆盖用户稳定布局；
- Semantic Drop 与 Drop Intent 状态机；
- 对齐参考线；
- 多选边界；
- ChangeSet 的 Keep / Revert；
- stale fail-closed；
- reduced-motion；
- Human 与 Agent 在同一空间工作。

### 3.4 明确废弃或降级

- 把 Huabu 视觉系统当成 LCOS 视觉系统；
- 统一白卡节点；
- 所有对象都套同一个标题栏与矩形框；
- DotGlyph 成为所有对象的主身份；
- Agent 状态抢过文件内容和项目材料；
- 把 Context / Workflow 仅做成同一批节点的重新排版；
- 把 Frame 等 Huabu 领域实体引入 LCOS Core；
- 用早期前端 Skill 把 PASS8 规则冻结成永久产品真理。

### 3.5 当前地位

```text
保留交互基础设施
废弃统一白卡视觉与产品规则外溢
```

## 4. 第三代：Spatial + 三大独立工作现场

### 4.1 当时解决的问题

第三代解决 Main、Context、Workflow 长得像三胞胎的问题，并建立正式的数据与空间边界：

```text
Main      像 Spatial
Context   像 Heptabase / 幕布 / Obsidian
Workflow  像 Linear / Coze / Weavy
```

三者共享 Spatial Canvas 基础，但不是同一批节点换三种排版。

主要参考 Spatial、Heptabase、幕布、Obsidian、AFFiNE/BlockSuite、tldraw、React Flow/xyflow、ELK、Cytoscape/fCoSE、Linear、Coze、Weavy 和飞书文档。

### 4.2 正式数据流

```text
Project Truth
      │
      ▼
User / Agent Intent
      │
      ▼
Presentation
      │
      ▼
Renderer
```

冻结判断：

```text
Default ≠ Rule
Presentation ≠ Project Truth
Selection ≠ Membership
Renderer ≠ 新的数据副本
```

### 4.3 Main 规则

- 一个 Project 只有一张持续存在的主画布；
- 自由空间组织，不存在强制顶层 Arrange Mode；
- 内容和材料必须拥有真实身体；
- 图片、文档页、网页和文件缩略内容优先于节点框架；
- Collection 是空间 Stack / Folder，不创建 Child Canvas；
- Grid 负责对齐和秩序，不把所有节点强制收纳；
- 自动整理必须先生成 Ghost Preview；
- 未确认不得覆盖 Canonical Canvas 坐标。

### 4.4 Context 规则

- 不得把 `Scope.nodes` 无脑全塞进 Context；
- 当前对象集合来自用户/Agent Intent、Saved View、明确加入与启发式建议；
- Outline、Mind Map、Relation Graph、Conversation Reading 是同一数据的不同投影；
- 来源必须明确且可理解；
- 来源链可移动、剪切、拼接并平行存在；
- Context 偏纵向、阅读、层级、聚焦与定位；
- 幕布式 Outline 与 Mind Map 共享层级；
- Obsidian 式 Relation Graph 允许多中心；
- Renderer 默认值只是建议，用户和 Agent 可覆盖。

### 4.5 Workflow 规则

- Workflow 偏横向、连接、动作、能力与执行；
- Action-first，Material 是引用或附件；
- Skill、Agent、Run 可以具有真实技术身份；
- Gate、Trigger、Input、Output 只能是软语义或 Presentation Tag；
- 不要求完整 DAG 才能 Run；
- 用户框选任意对象也能交给 Agent；
- 空白处也允许发起 Agent 工作；
- 不成为 n8n / BPMN 克隆。

### 4.6 Shared Spatial Engine 规则

- Main、Context、Workflow 共享相机、选择、拖拽、框选和边缘平移基础；
- tldraw 只提供 Infinite Canvas 与 interaction session 思想；
- xyflow 只提供交互、局部订阅与节点/边分层参考；
- ELK 用于有方向、层级和 Workflow 布局；
- fCoSE 用于 Obsidian 式多中心关系网；
- 布局算法运行于 Worker；
- 自动布局只输出 Ghost；
- 用户固定节点和稳定锚点必须保留；
- 高频 viewport、hover、selection 不得触发全图业务重渲染。

### 4.7 当前不足

- 架构成熟度高于 GUI 落地；
- Mind Map 尚未达到幕布式同构编辑体验；
- Context 编辑能力不足；
- Workflow 布局、连线和直接操纵仍不完整；
- 节点视觉身体仍经常被统一矩形外壳限制；
- Workbench、Source Chain 等大型组件仍不像真正积木。

### 4.8 当前地位

```text
第三代 = 正式数据、Presentation、Canvas 与三大 Surface 架构
第四代必须建立在第三代之上，不能推翻其真相边界
```

## 5. 第四代：Glaze + Glyth 空间工作语言

### 5.1 当时解决的问题

前三代依然容易把 GUI 做成：

```text
统一矩形节点
+ 白色卡片
+ 小图标
+ 状态标签
```

第四代要让 LCOS 成为一套可以由本地 Agent 搭建、组合、呼吸、表达轻重与关系的空间工作语言。

### 5.2 Glaze 的定义

```text
Glaze
= Catalog
+ Physics
+ Visual Materials
+ Agent Composer
```

Glaze 不是一个围栏、区域或 Workbench，也不是某个单独组件。它是整套空间组件、视觉材料、直接操纵和 Agent 搭建系统。

### 5.3 Glyth 的定义

Glyth 是 Glaze 的拟生语义角色：

- 活着的状态标点；
- 具有注视、呼吸、眨眼和轮廓形变；
- 可以沿组件边界、角落和路径活动；
- 根据 selection、running、review、error 等状态连续 morph；
- 表达 Agent/系统当前注意力和动作；
- 不拥有业务状态；
- 不成为 Project Entity；
- 不替代文件、节点和组件的真实身份。

### 5.4 Matrix Activity

参考 ROG AniMe Matrix 的离散活性，但不复制具体造型：

- RGB 点阵；
- 密度；
- 色相；
- 波纹；
- 方向；
- 聚散；
- 工作与处理状态。

Matrix 是活性材料，不是普通状态灯。

### 5.5 Light Segment

参考 Nothing Glyph Interface 的分段光语言，但不复制具体产品造型：

- 结构；
- 边界；
- 路径；
- 进度；
- 方向；
- 组件连接与状态变化。

Light Segment 是空间结构语言，不是装饰灯条。

### 5.6 动效参考边界

- Glyth 动画借鉴 Bloub MIT 项目的 gaze、blink、呼吸和 morph 思想；
- 可以吸收用户提供的 Glyth HTML 原型形态；
- 不宣称复制 Grok/xAI 官方视觉资产；
- Glyth 动效使用共享时钟；
- 后台、视口外和 Reduced Motion 下必须降级。

### 5.7 组件形态规则

组件可以拥有：

- 无壳；
- 半壳；
- 局部边界；
- 开放结构；
- 非矩形轮廓；
- 内容身体；
- Matrix 身体；
- Light Segment 身体；
- 多种视觉材料组合。

禁止所有组件无条件套同一个 `SurfaceFrame`、标题栏和白色矩形底卡。

### 5.8 Agent 积木搭建规则

Agent 至少应能：

- 创建组件；
- 选择合适组件类型；
- 设置位置、范围和形态；
- 放置内容；
- 调整文字；
- 标注重点；
- 设置视觉轻重；
- 建立节点、组件和上下文关系；
- 组合或拆解组件；
- 保存为 Presentation；
- 在 Main、Context、Workflow 中使用不同组合。

用户不强求必须手动搭出漂亮系统，但 LCOS 必须为本地 Agent 提供足够强、足够美观、可理解且可验证的搭建语言。

### 5.9 Grid 规则

Grid 不只是坐标吸附：

- 不同节点和组件可以拥有不同网格密度；
- Matrix 可以成为状态和节奏表达材料；
- Agent 可以通过 Grid 建立轻重、秩序和对齐；
- Grid 整理应保留节点大致原位；
- 只摆正歪斜和未对准点阵的节点；
- 不把全部节点强制排成没有缝隙的收纳状态；
- 必须适配不同节点尺寸。

### 5.10 关系表达规则

关系不得只依靠淡色连线。以下信息应共同表达关系：

- 节点形态；
- 体量；
- 距离；
- 边界；
- 色阶；
- 路径；
- Matrix 活性；
- Light Segment；
- 文字标签；
- 动态方向与状态。

### 5.11 直接操纵规则

- 组件不得只能拖标题栏；
- 用户应能从合理的组件身体区域直接移动；
- 文本选择、滚动、输入等内容交互区域可以阻止组件拖动；
- Resize、连接、编辑、拆分入口按距离渐进披露；
- Workbench 必须成为局部工作桌面，而不是静态页面列表；
- 组件必须能够被移动、缩放、组合、拆解与重新绑定。

### 5.12 当前实现债务

- 多数组件仍被 `SurfaceFrame` 压成矩形卡；
- Workbench 主要依赖标题栏拖动；
- Catalog 还不足以表达完整组件体系；
- Matrix 与 Light Segment 仍接近单比特指示灯；
- Glyth 的眼神、轮廓 morph 和状态表现不足；
- Body-level 操纵不完整；
- GUI 尚不能清楚证明 Agent 可以像搭积木一样构建工作现场。

### 5.13 当前地位

```text
第四代 = 最新组件形态、动态语言和 Agent 搭建规则
优先级高于第二代统一白卡规则
必须建立在第三代正式数据与 Presentation 架构之上
```

## 7. 施工冲突裁决示例

### 7.1 旧 Skill 要求所有节点使用统一卡片

裁决：拒绝。第二代统一白卡规则已被第四代组件形态规则替代。

### 7.2 Glaze 组件想修改 Project Truth

裁决：拒绝。第四代不能突破第三代 Project Truth / Presentation 边界。

### 7.3 Huabu Ghost Preview 与 Glaze Agent Composer 冲突

裁决：保留 Ghost。Agent Composer 的布局和组件修改仍必须先形成可审查 Preview，再由用户确认。

### 7.4 AdFrame 需要打开沉浸式 PDF/PPT 预览

裁决：保留。它属于第一代仍有效的 Preview/Review 子能力，不影响新 App Shell。

### 7.5 Workflow 被实现成固定 DAG 编辑器

裁决：拒绝。违反第三代 Workflow 软语义和“两次点击内交给 Agent”的规则。

### 7.6 Glyth 成为项目节点或业务规则中心

裁决：拒绝。Glyth 只表达系统注意力和动态语义，不拥有业务真相。

### 7.7 Matrix 和 Light Segment 只剩装饰效果

裁决：不通过。它们必须表达状态、结构、路径、强弱或方向，不能只是背景装饰。

## 8. 后续 GUI 审查必问

每次 GUI 改动至少回答：

1. 这项能力属于哪一代？
2. 它是应保留的基础，还是已经废弃的历史规则？
3. 是否改变 Project Truth、Presentation 或 Canonical 坐标？
4. 是否把默认建议错误写成强制产品规则？
5. 是否把不同组件重新压成统一白卡？
6. 是否让真实内容退居状态图标之后？
7. 是否允许 Human 与 Agent 直接操纵？
8. Agent 改动是否先形成 Ghost / ChangeSet？
9. Main、Context、Workflow 是否仍能一眼区分？
10. Matrix、Light Segment 与 Glyth 是否在表达真实状态，而非装饰？

只要其中任一项无法回答，就不能把该 GUI 改动称为正式收口。

---

## 9. 一句话版本

> 第一代提供审阅能力，第二代提供 Agent 协作机制，第三代定义 LCOS 的空间与数据架构，第四代负责让整套系统真正长成自由、灵动、可组合、可由本地 Agent 搭建的 LCOS。
